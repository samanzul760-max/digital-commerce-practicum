# 三角色数字商贸实训闭环设计

## 目标

在保留现有 LearnEC 参考页面的信息架构、共享 Shell、视觉基线和未提交改动的前提下，补齐学生、教师、管理员三类工作流，并让业务数据以服务端持久化结果为准。

本设计覆盖：

- 学生：计划发布、学习、保存草稿、提交、退回、重提、评分、刷新查看结果；
- 教师：班级、学生、作业、公告、课堂执行、审核、退回和评分；
- 管理员：计划、课程目录、案例、任务、成员、虚拟组、邀请、申请审批、培训室管理；
- 扩展入口：进度、通知、资源、数据中心、审计、模板和比赛；
- BDD、TDD、Playwright 用户路径和发布前安全审计。

本阶段不包含远程部署、生产数据库操作、迁移、`db push`、`db reset`、`.env` 修改或服务重启。

## 角色与权限

权限采用“角色 + 数据范围 + 操作能力”，不把角色简单等同为固定页面集合。

### 学生

学生可查看已发布计划、课程、任务、授权资源、个人进度、通知、提交历史、退回反馈和评分结果；可保存草稿、提交版本、修改退回内容并标记通知已读。学生不能读取草稿计划、他人提交、审核队列或培训室管理数据。

### 教师

教师可查看授权组织/培训室范围内的课程、资源、进度、通知、班级和学生摘要，并管理自己负责的班级。教师可发布班级作业、发布公告、记录课堂执行、查看任务状态、退回提交、评分和补充反馈。教师默认不能修改全局计划结构、成员角色、培训室生命周期或全局权限，但可按明确授权增加查看或操作能力。

### 管理员

管理员拥有授权培训室内的全局管理能力，包括计划发布、课程目录、案例、任务、成员、虚拟组、邀请、申请审批、资源、培训室设置、数据中心、审计、模板和比赛入口。

### 权限执行

- 页面导航根据查看能力显示入口；
- 直接访问 URL 时页面不渲染无权限业务内容；
- API 在每次读取和写入时校验会话、组织、培训室、班级范围和具体能力；
- 高风险操作单独校验，例如发布、成员变更、审批、退回、评分、培训室设置和导出；
- 前端权限判断只用于提前反馈，不能替代服务端校验。

## 数据与服务边界

项目当前存在两类服务端持久化：计划、目录、通知和部分管理数据由 `server/utils/practicum-repository.ts` 保存；班级、作业分配、学生任务、提交版本和评分由 Prisma 数据模型保存。页面不直接访问其中任何一种存储。

统一要求如下：

1. 页面通过 `usePracticumServer` 或页面级 `$fetch` 调用服务端 API。
2. 服务端响应是页面业务状态的唯一来源。
3. `usePracticumStore` 仅保留界面状态、身份显示和暂时性的表单状态，不再作为业务数据 fallback。
4. 刷新页面重新读取服务端；localStorage 中的旧计划、提交、评分、通知和成员数据不得覆盖 API 响应。
5. API 错误显示 error 状态，不显示伪造的成功结果。
6. 写操作返回服务端实体，成功后以返回实体更新页面或重新读取当前资源。
7. 重复提交、发布和评分使用幂等键或服务端状态校验，避免重复版本、重复任务和重复通知。
8. 已有存储结构无法表达公告、课堂执行、模板或比赛详细字段时，先显示真实 empty/not-configured 状态并记录缺口；不得用 localStorage 模拟持久化成功。

除非后续得到明确授权，本设计不修改 Prisma schema、迁移、数据库连接、`.env`、部署脚本或远程环境。

## 核心用户流程

### 学生闭环

`计划发布 -> 学生刷新看到计划 -> 进入学习 -> 保存草稿 -> 提交版本 1 -> 教师退回并填写反馈 -> 学生刷新看到 RETURNED -> 修改并提交版本 2 -> 教师评分 -> 学生刷新看到 GRADED、分数和反馈`

提交规则：草稿不产生不可变版本；每次提交产生递增版本；退回必须有反馈；重提保留历史版本和反馈；评分必须满足必填评分项；重复提交不能产生重复版本。

### 教师工作台

`进入班级 -> 查看学生 -> 发布作业 -> 发布公告或课堂任务 -> 查看课堂执行和任务状态 -> 打开审核队列 -> 退回或评分 -> 回到班级查看结果`

教师审核数据只包含教师有范围权限的班级和学生。退回、评分和公告发布成功后，页面显示服务端返回状态，并支持刷新验证。

### 管理员工作台

`计划/课程目录 -> 案例/任务 -> 成员/虚拟组 -> 邀请/申请审批 -> 培训室设置与生命周期 -> 资源/数据/审计/模板/比赛`

每个入口必须连接真实 API，或显示明确的 empty/not-configured 状态；不允许空白页和假成功按钮。

## 页面与交互

三种角色共用现有 `PracticumShell`、侧边栏、顶部栏、共享 CSS token 和状态组件。页面内容随能力变化，但全局导航位置、身份入口和主要视觉层级保持稳定。

所有受影响页面提供：

- loading：请求过程中不展示旧业务数据；
- empty：服务端无数据时显示空状态；
- error：请求失败时显示错误和重试操作；
- forbidden：不渲染管理数据、表单或操作按钮；
- success：成功后以服务端返回数据更新；
- confirmation：删除、发布、退回、评分、重提等高风险操作明确确认；
- mobile：375px、768px、1024px 和 1440px 下无横向溢出和内容重叠。

保持 LearnEC 参考页面的主要信息架构和现有视觉交互，但不复制源站品牌、文案、私有接口或受保护资源。

## 分阶段实施

### 阶段一：学生闭环与权限基础

固定学生服务端读取、提交版本、退回、重提、评分和刷新结果；补齐三角色登录、路由和 API 权限基础；清理学生主流程的 localStorage 业务 fallback。

### 阶段二：教师工作台

补齐教师班级范围、作业发布、公告、课堂执行、任务跟踪、审核列表、退回和评分页面及 API。

### 阶段三：管理员基础管理

补齐计划、课程目录、案例、任务、成员、虚拟组、邀请、申请审批和培训室生命周期；优先复用已有服务端仓库和 API。

### 阶段四：扩展入口与发布验收

补齐进度、通知、资源、数据中心、审计、模板和比赛入口；对于暂时没有后端数据结构的能力，先提供真实空状态和权限边界，不伪造业务成功。

阶段之间不混入无关重构。每阶段完成后必须保持前序阶段测试通过。

## BDD、TDD 与 Playwright

每个新增行为遵循：BDD 场景 -> TDD RED -> 最小实现 -> TDD GREEN -> 必要重构 -> 用户路径验收。

核心 BDD 需要包含 Given、When、Then，并验证：

- 计划发布前学生不可见，发布后可见；
- 提交产生递增不可变版本；
- 退回没有反馈时失败，有反馈时成功；
- 学生刷新后能看到退回、重提和评分结果；
- 教师只能操作授权范围；
- 无权限角色直接访问 URL 和 API 都被拒绝；
- API 失败显示错误状态；
- 空数据显示空状态；
- 清除或篡改 localStorage 不改变服务端结果；
- 重复提交不会产生重复版本或重复任务；
- 移动端核心页面没有横向溢出。

Playwright 只验收核心用户路径：学生闭环、教师审核闭环、管理员计划发布、权限隔离和移动端核心页面。超时场景停止并标记 `UNVERIFIED`，不自动改成通过。

## 并行协作边界

只有文件集合互不重叠的任务才并行执行：

- 服务端权限/API：`server/`、权限领域文件和对应 API 测试；
- 教师页面：教师页面、教师组件和教师页面测试；
- 管理员入口：对应管理员页面和页面测试；
- 学生服务端来源：学生页面、服务端 composable 和学生闭环测试；
- 主线程：设计文档、任务串联、共享 Shell 冲突处理、集成测试、全量验证和交付报告。

子任务禁止修改共享 Shell、Prisma schema、迁移、`.env`、部署脚本，也禁止同时编辑同一个测试文件。子任务只在自己的文件范围内提交结果，由主线程检查 diff 后串联。

## 服务器、数据库和 Git 安全

- 只使用当前本地项目目录；
- 每次修改前运行 `rg --files` 和 `git status --short`；
- 不运行 SSH、远程命令、PM2、Nginx、Docker 变更或部署脚本；
- 不执行 Prisma migration、`db push`、`db reset`、schema 修改或数据库连接切换；
- 不删除 `.nuxt`、`.output`、`node_modules`、`.data` 或测试产物；
- 不使用 `git reset --hard`、`git clean`、整仓 `checkout/restore`；
- 保留用户已有未提交修改；
- 只在当前已有本地服务上做只读健康检查，解决端口冲突时不启动第二个服务；
- 每次集成前检查变更文件清单，确认没有越界路径；
- 最终报告明确列出是否修改服务器、数据库、迁移、部署脚本和用户已有改动。

## 验收标准

只有在以下证据齐全时才标记某阶段完成：

1. 相关 BDD/TDD 测试已先红后绿；
2. 核心 Playwright 场景通过，超时项明确标记 `UNVERIFIED`；
3. typecheck 通过；
4. build 通过；
5. `git diff --check` 通过；
6. 1440px 与 375px 页面检查无横向溢出、重叠、控制台错误；
7. API 失败、空数据、无权限和刷新状态均有证据；
8. 变更不包含远程服务器、数据库迁移、`.env` 或用户已有无关改动；
9. 完成、部分完成、缺失和未验证能力在报告中分开列出。
